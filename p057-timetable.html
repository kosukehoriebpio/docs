2026-06-15 確定。開催形式 = オンライン（Google Meet）。 堀江判断確定: A=a（動くプロトタイプ必須を維持）/ B=c（1チーム協働＋審査員ベンチマーク比較）/ C=c（メンターへはsnapshotシート＋禁止ワードのみ共有、選考判定は別ブリーフィング）

1. Overview

  • 開催日: 2026-06-19（金）
  • 形式: オンライン開催（Google Meet メインルーム + breakout rooms）。参加者・メンター・運営はそれぞれの環境からオンラインで参加する
  • 時間: 10:00-18:30
  • 対象: 2028卒（2026/6時点で大学3年生）。集客ページは「未経験者でも可」で公開済みのため、Lv1（完全未経験）〜Lv2（ChatGPTは触ったがツールで"作る"のは初めて）が混在する前提。標準は Lv2 だが、AI集中講義の前半に未経験者向け基礎を内包し、メンターの重点フォローで Lv1 も当日中に立ち上げる（非エンジニア／ノーコード前提）
  • 参加人数: 6/19時点確定5名、最大10名、最少催行3名
  • 採用プログラム: Plan C確定（AI集中講義 × 業務改善コンテスト）
  • 選考方針: 「選考要素あり / 見極め重視」確定。学生には個別フィードバック提供を告知しない
  • BPO課題テーマ: TBD（経理 / 労務 / 総務のいずれか）。最終確定期限は 2026-06-17 18:00
  • 成果物ルール（Decision A=a: 動くプロトタイプ必須を維持 / 2026-06-15確定）:
    • 必達目標: no-code で動くプロトタイプ（Gem + GAS など）を「必須」として打ち出す
    • 未達時の審査継続フォールバック（silent fallback）: 設計書 + プロンプト集 + 想定入出力 + テストケース
    • 15:30 実装チェックで未完成のチームはフォールバック提出物の並行作成に切り替え、最終審査はどちらの提出物でも受け付ける
  • オンライン必須準備: 各自の通信環境・接続安定性の事前確認、Google Meet リンク共有、breakout room 設定、学生各自のPC・ブラウザ動作確認、リモート講師の接続テスト

4. 2-Layer Evaluation Design + Pass Criteria

Layer 1: 学生に見せるコンテスト評価

評価軸 見る内容 備考
課題定義 BPO課題の理解、真因の捉え方 設計の筋を重視
解決策設計 業務フロー、ユーザー体験、実行現実性 動作有無だけで決めない
AI活用の質 プロンプト設計、AIへの役割分担、検証の仕方 no-code 前提
実証・伝達 デモ、想定出力、テストケース、発表の明快さ 動作デモ未完成でも審査可能

Layer 2: 社内用の個人見極め

  • 常時5軸採点はやめ、以下の3 snapshot だけを記録する。
  • 記録形式は Strong / Neutral / Concern の3値 + 1行メモとする。
  • ※当日メンターが現場で使う配布物はこの Snapshot シート。発表後に集約・解釈する詳細な4観点フレーム（Lv1–Lv4）は docs/materials/evaluation-rubric.md §3 Layer2 を参照。
Snapshot 時点 主に見ること 記録者
1 14:25 設計レビュー 課題構造化、仮説の質、役割の取り方 担当メンター
2 15:30 実装チェック 学習吸収、詰まり時の自走、協働姿勢 担当メンター
3 最終発表時 伝達力、当事者意識、価値観の相性 メンター + 審査員

早期選考候補の暫定 pass criteria

  • 暫定基準。凜子の選考設計との整合が必要（RC-D01）。
  • 候補者に上げる条件案:
    • Snapshot 3回のうち2回以上で Strong を獲得している
    • 課題構造化 と 自走 / 協働 の両方で Concern が無い
    • 最終発表時に、自分の担当範囲を具体的に説明できる
    • 遅刻・離脱・コミュニケーション不全が無い
  • 凜子との整合後に「早期選考通過候補」「保留」「見送り」の3区分へ確定する。

メンターへの共有範囲（Decision C=c 確定 / 2026-06-15）

  • メンターに渡すもの: Snapshot 観察シート（Strong/Neutral/Concern + 1行メモ）と、禁止ワード（「個別FBします」「早期選考確約」等の不用意な約束を当日口にしない）。
  • メンターに渡さないもの: 早期選考の通過閾値・選考判定。これは人事（堀江 / 凜子）の別ブリーフィングで管理する。
  • 司会台本と選考判定ブリーフを分離し、評価品質を保ちつつ学生への不用意な発言を防ぐ。

7. Horie Decision Items（2026-06-15 確定）

A. 成果物難易度の置き方 → ✅ 決定: a（動くプロトタイプ必須を維持）

Option 内容 判断
a 「動くプロトタイプ必須」を維持する ✅ 採用
b 正式成果物を「設計書 + プロンプト集」まで緩和する —
c 6/17 までの dry-run 計測で a / b を決める 推奨だったが a を選択
  • 補足: 「必須」と打ち出すが、§1 の silent fallback（未完成時は設計書+プロンプト集で審査継続）を保険として維持するため、サイレント失敗（審査不成立）は回避される。RC-C06 のリスクは fallback で吸収。

B. 3-4名時のコンテスト性の作り方 → ✅ 決定: c（1チーム協働＋審査員ベンチマーク比較）

Option 内容 判断
a 1チーム協働 + 達成基準チャレンジ化 —
b 2小チームに分けて疑似対戦する —
c 1チーム協働 + 審査員ベンチマーク比較にする ✅ 採用
  • 推奨理由: 初心者を無理に分割すると支援密度が下がる。1チーム協働を維持しつつ、審査員ベンチマーク比較で contest frame だけ残す方が安定する。

C. 「FB非開示」と評価記録の両立方法 → ✅ 決定: c（snapshot sheet + 禁止ワードのみ共有、選考判定は別ブリーフィング）

Option 内容 判断
a メンターへ選考用途・通過閾値まで全面共有する —
b メンターへは観察軸だけ共有し、通過判定は人事のみが持つ —
c メンターには snapshot sheet と禁止ワードだけ共有し、司会台本と選考判定は別ブリーフィングに分ける ✅ 採用
  • 推奨理由: 評価品質を落とさず、学生への不用意な「FBします」発言も防ぎやすい。
